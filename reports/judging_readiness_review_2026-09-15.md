## 2. 제품의 중심 문장과 범위

> 장병과 가족·연인·친구가 강원 여행을 함께 준비하고, 장병은 자기 복귀 기준에 맞춰 여유를 조정하며, 다녀온 하루를 기록한다.

가장 기억에 남겨야 할 장면은 **함께 고른 장소를 한 곳 줄이거나 체류시간을 바꾸자 복귀 여유와 도보 부담이 어떻게 달라지는지 비교하는 화면**이다. 실제 교통을 예측하거나 부대 복귀를 보장하는 서비스로 설명하지 않는다. 이동은 거리 기반 추정이며 혼잡·날씨·동행 여유의 가정을 구분해 보여준다.

공동 일정과 개인 복귀 정보는 구분한다. 그룹에는 사용자가 확인한 여행 계획을 공유하고, 개인 복귀시각·출타 진행·스탬프를 자동 전송하지 않는다. 공개 한 수 링크에는 서버가 허용한 관광지·권역·질문만 보낸다. 이 구분 자체가 장병과 동행자가 안심하고 계획을 나눌 수 있는 제품 가치다.

로그인·서버 저장·오류 대응은 핵심 경험의 완성도 근거로 설명한다. 새로운 AI 애니메이션, 추가 지역, 보상 기능 확대, 소셜 피드·랭킹은 남은 기간의 우선순위로 두지 않는다. 기존 정상 TourAPI 검색·목록·상세·사진·일정 연결과 Kakao 지도는 유지한다.

| 2. 동행 그룹과 함께 준비하기 | 가족·연인·친구가 서로 다른 기기에서 같은 여행을 준비 | 그룹 초대 → 공동 일정 보기·편집 → 동행 조건 확인 → 내 여행 가져오기 | 서버 그룹 저장·공유 범위·개인 사본 구분. 기획력·완성도 |

## 5. 지정 9쪽 기본 양식과의 대응

지정 양식의 항목과 순서를 유지한다. 기본 양식은 9쪽이며 **6번 기능 설명 페이지를 복사해 핵심 기능 최대 5개를 설명할 수 있다.** 기본 9쪽을 총 페이지 상한으로 오해하지 않는다. 최종 페이지 수는 실제 편집 후 확인하되 PDF는 10MB 이하로 만든다. [양식·제출 매뉴얼 확인](submission_assets.md)

### 제출 전 새로 확보할 증거

1. **실제 API 사용 시나리오**: 호출 시각·지역·성공/실패·장소 참조를 남기고, 실제 화면에서 검색한 장소를 일정에 담아 조정·저장한다. 키나 토큰은 촬영하지 않는다. 장애 대체 자료와 mock 결과는 따로 표시한다.
2. **다중 사용자 시나리오**: 장병 A와 동행자 B가 다른 브라우저에서 초대·공동 수정·개인 사본 설정을 완료한다. 동시 수정 충돌과 재접속은 기존 회귀 검사로 확인한다.
3. **대표 여행 조건표**: 실제 선택한 날짜의 운영·휴무·예약·신분확인·주차/접근 안내를 공식 출처와 확인일로 기록한다. 미확인 항목을 ‘문제없음’으로 치환하지 않는다.
4. **실제 사용자 관찰**: 가능하면 장병·동행자 3쌍 정도가 설명 없이 여행 만들기·초대·조건 변경·출타 시작·완료를 수행하도록 본다. 완료 여부·도움이 필요했던 지점·오해한 문구를 기록한다. 모집하지 못했다면 내부 시나리오 검사로만 표기한다.
5. **심사 접근 리허설**: 지정 전용 테스트 계정과 공개 URL로 새 세션에서 진입한다. 안내된 ID `openapi`, PW `2026openapi!`는 심사용 규격이며 실제 생성·동작 확인은 별도 해야 한다. 기존 공통 체험 비밀번호 1234만으로 제출 조건을 충족했다고 가정하지 않는다.

정상 관광 기능을 줄여 검사 결과를 좋게 만들지 않는다. TourAPI 운영계정·공모전 증설은 문의 준비, 발송, 접수, 승인 상태를 나누어 기록한다. 현재 승인량이나 초기화 시각은 확인값만 사용한다. 원문 응답의 운영 DB 적재는 별도 저장 조건을 해결한 뒤 판단한다. [호출량 확대 전략](api_capacity_strategy.md), [운영 정책](tourapi_operations_policy.md)

## 8. 제출 가능한 상태의 판단

핵심은 기능 개수 증가가 아니라 다음 사실을 함께 입증하는 것이다.

- 처음 온 동행자가 왜 이 서비스를 쓰는지 이해하고 같은 여행을 열 수 있다.
- 부모 여행과 친구 여행의 조건이 섞이지 않는다.
- 개인 복귀 기준을 사용자가 정하며 계획·실제 출타·공유 범위가 구분된다.
- 공사 OpenAPI를 실제로 사용한 장소가 선택·시간표·방문 확인으로 이어진다.
- 실제 실행한 시나리오, 공개 배포, 기능설명서가 같은 버전을 설명한다.

이 문서는 심사 준비를 위한 개선 우선순위이며 수상 순위나 점수를 보장하지 않는다. 구현 완료는 코드, 검사 완료는 결과, 배포 완료는 운영 상태, 제출 완료는 접수 확인으로 각각 기록한다.
